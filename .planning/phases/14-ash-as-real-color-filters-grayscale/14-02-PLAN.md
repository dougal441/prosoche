<objective>
Settle locked decision **D-14-02**: probe whether `AXToggleColorFiltersIntent`'s `state`
**response** parameter is consumable as a magic variable. If it is, Ash could DETECT a
pre-existing user filter and leave it alone, instead of relying on default-ON plus an
onboarding disclosure the user has to read in order to opt out. That is the difference
between an accessibility risk that is **mitigated** and one that is merely **disclosed**.

**This plan runs in parallel with the tracer and must not block it.** The shipped fallback —
the opt-out flag plus disclosure — is already a locked user decision and is being built
regardless. This plan buys information, not a dependency.

**The question is two questions, and conflating them is how it gets answered wrongly.**
(a) Does the action bind an output at all? (b) Does that output carry the state *before* the
operation or *after* it? Only "before" makes preservation buildable with the deterministic
Turn form this product uses. An "after" answer means preservation would need the Toggle form,
which the phase's own design statement rules out because a Toggle desynchronises from
snapshot ownership the first time a run is interrupted — so an "after" answer is a **conflict
to surface, not a design to adopt**.

Purpose: SAFE-02's real threat surface in this phase is clobbering a user's own Color Filters
setting — set deliberately for colour-blindness, migraine or low vision. AUDIT-02's remaining
open item on this capability is exactly this untested lead, recorded in spike 005's Open
Questions.

Output: spike 011, with a verdict, and that verdict promoted into the two record surfaces the
project's recording duty names.
</objective>
