<objective>
Teach the three artifact-side checkers about grayscale, and prove the widened capture guard is
load-bearing for the third group rather than merely wider.

**One of these files currently asserts the exact opposite of what the phase ships**, and it has
been red since plan 14-01's first rebuild by constraint D-CHECKER. Inverting it is a deliberate,
recorded edit and not an incident — but it must be inverted **asymmetrically**, because half of
that assertion is stale and the other half is the standing guard against shipping a macOS action
to an iPhone in exchange for a green validator.

**Another of these files will pass after this phase with no edit at all, while covering nothing
new.** Its site table counts exactly three identifiers, its device-property allowlist names
exactly two properties, and its bootstrap-seed assertion loops over exactly two groups. None of
those fails when grayscale is added — they simply do not look. A green run on the unedited file
is a false reassurance of precisely the kind its own docstring warns about.

**And the guard whose group derivation changed in 14-01 needs a control that can tell
generalisation from mislabelling.** The retired derivation was a two-way test whose else branch
named volume, so a third identifier would have been silently labelled wrong rather than raising.
A control that only proves the guard still fires does not distinguish those two worlds.

Purpose: in this codebase the artifact checkers deliberately duplicate the build guards, proving
the shipped XML from disk without importing its producer. A guard family that grows a third
member without the checkers growing with it leaves the site tables certifying a build as safe
while covering two thirds of it.

Output: the static suite is green again, with grayscale genuinely inside it.
</objective>
