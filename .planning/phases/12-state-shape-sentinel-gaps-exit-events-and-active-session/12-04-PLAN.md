<objective>
Close the **third key nobody named**, then convert the whole defect family into a
permanent build error.

`12-RESEARCH.md` ran the full-codebase sweep the ROADMAP asked for, but generalised it
beyond the two chartered keys: every literal `WFDictionaryKey` read from `State` or
`Reloaded State`, resolved against the seeded template. It found
`profile_snapshot.create_target_url` — a **dotted** read of a leaf the bootstrap does not
establish, sitting on `route_exit()`'s Create branch, i.e. on the exact exit path this
phase is chartered to make survivable. `profile_snapshot` itself is seeded (goal,
phone_purpose, reclaim_for, deliberate_leisure_definition, enabled_exits, synced_at,
note_content_hash); `create_target_url` is not. Choosing the Create exit on a clean install
hard-errors at that read, *after* `exit_events`, both `pending_exit` leaves and
`exit_selection_counter` have been written and `save_state("Reloaded State")` has already
run. That is arguably the single most likely first-exit crash in the whole phase surface.

The phase's own governing rule — "fix whole classes, never site-by-site" — is why it is in
scope: same defect class, same code path, same requirement IDs.

But the fix is **not** a copy of the `pending_exit` shape, and the researcher deliberately
refused to guess it. Its consumer gate is a has-any-value test that must read **false**
when the user has not yet supplied a URL — and the `CLEARED_SENTINEL` is present and
non-empty, so a condition-100 gate over it reads **TRUE**, which would `openurl` the
literal string "null". That is the axis-7 trap exactly. This is the one place in the phase
where the sentinel-versus-`null` choice collides with an existing gate, and it changes an
emitted on-disk state contract, so it is rated `one-way` and gated with a
`checkpoint:decision` before the implementing task.

Then, the highest-leverage line in the phase: generalise `verify_state_seed()`'s read-side
scan from `settings_snapshot`-rooted keys to **every** literal key read from `State` or
`Reloaded State`. Run against the pre-phase tree that guard reported eight unresolved
key/source rows — exactly the set this phase closes. Landing it last turns the whole family
into a build error rather than a device error, permanently and for every future phase.

Binding constraints D-01..D-04 as stated in `12-01-PLAN.md` `<objective>` apply unchanged.

  <context>
**What is measured and certain.** `route_exit()`'s Create branch reads
`profile_snapshot.create_target_url` from `Reloaded State` into the variable
`Create Target URL`, then opens a **condition-100 (has any value)** gate over it. If that
gate reads TRUE the branch runs `is.workflow.actions.openurl` on the value. If it reads
FALSE the branch asks the user "Where should Create open?", validates the answer with a
second condition-100 gate, reloads state, re-proves session ownership with a condition-4
compare, saves the URL and opens it. So the first gate must read **false** on a clean
install or the user's very first Create exit opens a placeholder instead of asking them
anything. `profile_snapshot` is seeded; this one leaf is not; and a dotted read whose final
segment is absent raises "could not evaluate the key path".

**What is not settled by any document in this repository.** Whether `read_value()` — which
is `getvalueforkey` followed by `gettext` — applied to a JSON `null` leaf yields no-value
(gate false, correct) or the text "null" (gate true, wrong). `.claude/CLAUDE.md` documents
`"null"` coerced to a Number as false; it says nothing about `null` coerced to Text under a
has-any-value test.

**Why this is a one-way door.** It changes the emitted `state.json` contract that a device
adopts at the schema-4 rebuild, and it changes the gate semantics of a shipped exit route.
BD-06-A1 forbids a migration, a dual-key alias and read-time normalisation **by name**, so
reversing the choice later costs another forced schema bump and another total loss of
heat, gravity, pressure, the rolling windows and every `exit_stats[*].samples`.

**What the whole phase depends on.** Whichever option is chosen, Task 3's generalised
`verify_state_seed()` must end clean. Options A and B satisfy it by seeding the key; option
C satisfies it only through a single named, commented exemption plus a pending todo.
  </context>
