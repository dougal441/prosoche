## Phase goal (verbatim from ROADMAP.md)

> A user can import the Shortcut, run it manually for the first time, and get a working state.json plus a fully instructive Control Room Note — and every subsequent invocation routes correctly and never corrupts or duplicates that foundation.

**Success criterion 1 this plan owns:** running the Shortcut with no input, `OPEN` input, and
`CLOSE` input each route to the correct branch using iOS-26-compatible nested `If`/`Otherwise`;
unrecognised or empty input fails safe without corrupting state or hanging.

## Decision legend

Full D-14..D-26 legend in `02-01-PLAN.md`. The ones this plan turns on:

- **D-15** — Nested `If`/`Otherwise` only. `Otherwise If` is macOS-27+ and unusable at the iOS 26 target. Binding on this router and on every later Circle lookup.
- **D-16** — Three invocation modes distinguished by Shortcut Input: absent or empty → MANUAL, `OPEN`, `CLOSE`. Unrecognised input must fail safe.
- **D-23** — A unique `GroupingIdentifier` per control-flow block and per nesting level. This plan takes the router from one block to three, which is exactly where collisions appear.
- **D-25** — The validator can pass a broken shortcut. Routing correctness is asserted structurally against a decision table, not inferred from a green exit code.

branch, `CLOSE` to the CLOSE branch, anything else non-empty to a fail-safe branch that mutates

Purpose: every later phase hangs off exactly one of these four outcomes. A phantom OPEN from a
mis-typed automation would corrupt Heat and Pressure with an event that never happened, and a
hang on unrecognised input would strand the user with a modal they did not ask for. Both are
prevented here, structurally, before any behavioural logic exists to be corrupted.

**The fail-safe branch (BOOT-02).** This is a named design decision, not an oversight:
unrecognised input is inert by construction. It contains, and may only contain, a `Comment`
recording that rule and exactly one `Show Alert` telling the user that PROSOCHĒ received input it
did not recognise and took no action. It performs no file read, no file write, no dictionary
mutation, no Note creation, and no Note append — because treating a mis-typed or stray input as
a real tracked-app open would inject a phantom event into Heat and Pressure, and because a
branch that waits on anything is a branch that can hang. The alert's title and message are
display parameters and must use the display serialization with `￼` placeholders and
`attachmentsByRange` even if they interpolate nothing — the data-flow serialization on a display
parameter renders blank at runtime while the plist still validates (D-22, PITFALLS A2).

Close Block C, then Block O, then leave the outer gate's `Otherwise` (the MANUAL branch) and its
`End If` exactly as 02-01 authored them.

The comparands `OPEN` and `CLOSE` must be byte-identical to the strings the Control Room Note
tells the user to type, uppercase, with no surrounding whitespace — the normalisation in task 1
uppercases and trims the incoming value, so the comparands are the uppercase forms. Read them out
of the Note body rather than retyping them from memory.
