## Phase goal (verbatim from ROADMAP.md)

> A user can import the Shortcut, run it manually for the first time, and get a working state.json plus a fully instructive Control Room Note — and every subsequent invocation routes correctly and never corrupts or duplicates that foundation.

**Success criteria 4 and 5 this plan owns:** later manual runs never overwrite existing state or
create a duplicate Control Room Note; and missing or corrupt `state.json`, and a deleted Control
Room Note, each trigger safe self-healing recovery rather than failure, from any invocation mode.

## Decision legend

Full D-14..D-26 legend in `02-01-PLAN.md`. The ones this plan turns on:

- **D-14** — Monolithic graph, no internal `Run Shortcut` hops. Shortcuts has no subroutines, so "shared by all three modes" means hoisted above the router, never duplicated into each branch and never split into a helper shortcut.
- **D-18** — One JSON state file, one Apple Note. Both can be deleted by the user independently, and the architecture must not assume they fail together.
- **D-19** — State is bounded and versioned. The version is what makes corrupt-state detection cheap.
- **D-24** — Dictionary coercion: booleans read back as `1`/`0`, `null` reads back as empty, a nested read on a null parent breaks, and any value reaching an `If` passes through a `Text` action first.
- **D-25** — The validator can pass a broken shortcut. Idempotence and self-healing are proved as nesting properties of the plist, not inferred from a green exit code.
- **BD-05** — The Control Room is built on the four Notes actions, gated by UA-01's on-device confirmation, with a named file-based fallback.
- **DEV-02** — No file-existence-check action exists; the substitute is Get File with the not-found error suppressed, piped through Detect Dictionary.

  <action>
**Move, do not copy.** Shortcuts has no subroutine mechanism and D-14 forbids an internal
`Run Shortcut` hop, so the only way to share the state load across all three invocation modes is
to place it above the router. Lift the chain 02-01 authored inside the MANUAL branch — Get File,
Detect Dictionary, the `schema_version` read, its `Text` routing, and the bootstrap gate with its
Save File — out of that branch and place it immediately after the run-clock section and
immediately before the router's normalisation chain. The MANUAL branch keeps everything else it
had. Do not duplicate the chain into the OPEN and CLOSE branches: a second Save File anywhere in
the file is a defect this plan's own check rejects.

That single move is what makes BOOT-06 true — a missing `state.json` is rebuilt whether the run
came from a manual tap, from the OPEN automation, or from the CLOSE automation.

**Turn the presence check into the two-field validity gate (BOOT-07).** ARCHITECTURE.md §3 step 4
specifies a cheap two-field sanity check rather than full schema validation, because full
validation is itself a place a corrupt file can keep failing. Compute a single `Text` value
`State Present`, set to `yes` only when all three of the following hold and to `no` otherwise:
`schema_version` has any value; `schema_version` matches the expected version; and `profile` has
any value. Build it as nested single-condition `If`/`Otherwise` blocks, each with its own fresh
`GroupingIdentifier`, each testing a value that has already been routed through a `Text` action.
A Dictionary Value compared directly inside an `If` evaluates blank — a documented Shortcuts bug,
not a hypothetical one (D-24, PITFALLS A4, and the second hazard named in `src/CONFIG-BLOCK.md`).

Compare the version with the string-equals condition code on the text-routed value. Shortcuts has
no numeric-equals condition code — code 0 is "is less than" (PITFALLS A5) — so an equality test
built on a numeric code would silently misfire. Record that reasoning in the section `Comment`.

**One gate owns the split.** After `State Present` is computed, exactly one conditional tests it
with the string-equals code against `yes`:

- TRUE: the load path. `State` is already parsed and is used as-is. This branch writes nothing at
  all.
- `Otherwise`: bootstrap. The Create Folder action, the `state.json` `Text` template, Set Name and
  Save File live here and nowhere else. A corrupt document and a missing document take this same
  branch — they are indistinguishable at read time, since a partial write reads exactly like any
  other corruption — so the recovery must be identical and always safe regardless of cause.

Add to that branch a `Set Variable` recording that a recovery happened on this run, so the MANUAL
branch in task 2 can note it into the Control Room Note on a best-effort basis. Do not append to
the Note from the OPEN or CLOSE path; see the Note-check scoping decision in task 2.

**Normalise the two import answers** — the item 02-01 deliberately deferred and flagged in the
graph. Inside the bootstrap branch, before the `state.json` template is composed: map
`Import Descent` to exactly one of `Paradise`, `Limbo`, `Inferno` using nested single-condition
`If`/`Otherwise` blocks, defaulting anything unrecognised to `Limbo`, which is the documented
default in §7.1 and in the state schema. Map `Import Voice` into the template as a real JSON
boolean, remembering that whatever is written will read back as numeric `1` or `0` and never as
the strings true or false, so every later read of it branches on the number (D-24, and the first
hazard named in `src/CONFIG-BLOCK.md`). Write the normalised values into the template rather than
the raw answers, and remove the `Comment` 02-01 left flagging this as outstanding.

**Guard the nullable reads.** Every field in the state schema that is null on a freshly
bootstrapped document — `last_open_at`, `last_close_at`, `last_app`, `active_session`,
`cooldown_until`, and every key beneath `active_session` — must be guarded with a has-any-value
check before any nested key is read from it, because reading a child key of a null parent breaks
rather than returning empty. Phase 2 reads none of them yet. Add a section `Comment` immediately
above the load path stating the rule, so Phase 3 inherits it at the point of use rather than
rediscovering it the hard way.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `state.json` on disk → the behavioural engine | A user, iCloud sync, or a killed write can leave the file missing, truncated, or half-written; whatever comes back is fed to arithmetic that decides how hard to interrupt someone |
| The Control Room Note → the user | The Note can be deleted at any time by the user or by an iCloud conflict, independently of the JSON, taking the only onboarding surface with it |
| Repeat invocations → the two stores | Every automation firing is another chance to overwrite state or create a second Note |
| Notes permission prompt → an automatic OPEN | A first-use permission prompt during an automation appears at a moment the user is not looking at the screen |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-21 | Tampering | A later run overwriting valid state | critical | mitigate | Exactly one `Save File` exists in the graph and its enclosing control-flow chain is asserted to include the `State Present` gate on its otherwise-side, so a run with valid state cannot structurally reach it |
| T-02-22 | Tampering | Corrupt or partially-written `state.json` feeding arithmetic | critical | mitigate | The two-field validity gate rejects any document missing `schema_version`, carrying an unexpected version, or missing `profile`, and routes it to the same always-safe rebuild as a missing file; a parse failure never propagates past the gate |
