<objective>
Answer the one genuinely one-way question in this phase before any code walks through it.

Plan 11-05 adds a new field to the bootstrap `state.json` template (the Panic Escape flag) and
plan 11-06 changes an existing one (the fork label). On a device that already holds a
`state.json`, neither reaches it: the stored file passes the three-check validity gate and is
reused forever. The only mechanism that forces a rebuild is a `schema_version` change — which
is precisely how it was used once before, and which discards everything the device has
accumulated: heat, gravity, pressure, the rolling windows, the exit-learning record.

That is a data migration with no field-preserving path. Shortcuts offers none, and this project
has never built one. It is not a refactor, and it should not be decided by an agent mid-plan.

Purpose: put the door in front of the human before the agent walks through it.
Output: one recorded decision, with its cost stated, that plans 11-05 and 11-06 implement
without re-litigating.
</objective>

  <context>
    **Why this is being asked.** `fix_state_rebind()` in `tools/build_state_engine.py` bumped
    the version once before, for exactly this reason: a stored state file that still satisfies
    the runtime validity gate is reused forever, so a change to the seed template is invisible
    on an already-installed device. The function hardcodes both the replacement value and the
    acceptance tuple the gate compares against, so a change is a code edit in that function, not
    a data edit — and the template and the check literal must move together.

    **What a bump costs.** There is no field-preserving migration. Shortcuts provides no
    mechanism for one and this project has never built one. A device whose stored version is no
    longer accepted rebuilds its `state.json` from the template on its next run, discarding
    accumulated heat, gravity, pressure, the rolling windows, the session record and the
    exit-learning history. That is unrecoverable — the Apple Note keeps the human-readable
    ledger, but the machine state is gone.

    **What not bumping costs.** An already-installed device silently never receives the Panic
    Escape flag, so the removal path plan 11-05 builds cannot be exercised there; and it keeps
    showing the old fork label in its status and in the note's settings block after plan 11-06's
    rename. Fresh installs are unaffected either way.

    **What is known about the installed population.** DIST-03 is open — no iPhone is currently
    connected and Phase 8's real-iPhone import is still outstanding. However, device runs did
    happen earlier in the project (a build was device-verified on 2026-08-15 and one Circle has
    fired on a real device), so at least one device plausibly holds real accumulated state. The
    population is small and known to the developer; it is not zero by assumption.

    **A second, smaller disposition to settle in the same breath**, because plan 11-06 needs it:
    after the signed artifacts are renamed, do the old-named signed `.shortcut` files stay on
    disk in `artifacts/shortcuts/`? `docs/manifest_check.py` only asserts the rows it is given,
    so an orphaned file is invisible to it, and two plausible "current" imports sitting side by
    side is exactly the confusion the signed-name discipline exists to prevent. The dated
    archives under `artifacts/shortcuts/2026-08-*/` are historical records and are left alone
    either way, per the precedent set by quick task `260817-au7`.
  </context>
