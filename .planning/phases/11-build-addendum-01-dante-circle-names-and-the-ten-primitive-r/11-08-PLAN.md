<objective>
Two of the nine shipped interventions do nothing, and two later phases each shipped believing
otherwise.

`dimming()` and `silence()` read the `settings_snapshot.<x>` **container** and gate it on
"has any value" (condition 100), with the entire capture-and-apply body — the device read, the
snapshot write, the environmental write, the save, and even the "could not be captured, so
nothing was changed" fallback alert — in the arm that is taken when the container is absent.
`clear_snapshot()` clears the leaf and never the container, and its own docstring calls the
container a permanent bootstrap invariant. The gate is therefore permanently true, both
primitives take the `Nothing` arm on every run, and 44 environmental actions per fork are
unreachable — re-measured against HEAD `e6b96e3` in this session, not inferred: `dimming()` at
`tools/build_state_engine.py:706-742` and `silence()` at `:744-780` both still open on the
identical container-existence shape `11-REVIEW.md` (CR-01) found on 2026-08-17.

**This is not the defect Phase 16 fixed, and Phase 16 believed it was untouchable rather than
touching it by mistake.** Phase 16's own P0 was that a capture which DID happen was never
persisted to disk before the device changed — `save_state()` sourced `State`, but the OPEN arm's
last save of that dictionary ran above `universal_leaving()`, so a real capture written during a
dispatch rendering never reached `state.json`. Plan 16-01 fixed that ordering and it is correct
and unmodified by this plan. But `dimming()`'s own current docstring, added by that plan, states
outright: *"The condition-100 container gate (`snapshot_g`) and the numeric `> 0` capture gate
(`capture_g`) are UNTOUCHED by this change and must stay so — they are this project's input
validation over an absent or untrusted Get Device Details reading (T-16-03)."* That is true of
`capture_g` (the inner numeric gate on the freshly read `Captured Brightness`) and **false** of
`snapshot_g` (the outer container-existence gate, evaluated BEFORE `Get Device Details` even
runs): `snapshot_g` validates nothing about a device reading, because no reading has happened
yet when it fires. Phase 16 lumped both gates under one threat (T-16-03) and, believing both
were load-bearing input validation, deliberately left the actually-broken one alone. This plan
corrects that belief as part of fixing the gate.

The fix is small and already written elsewhere in the same file: `restore_managed_settings()`
gates its leaf numerically and puts its work in the reachable arm. This plan applies the
identical shape to `dimming()`/`silence()`'s outer gate, changing nothing about the persistence
fix, the D-01 zero floor, or the D-02 leaf removal Phase 16 already shipped.

Purpose: make two of BD-06's nine interventions actually intervene, correct the false belief
that stopped Phase 16 from finding this, and make the dead-arm shape a build failure rather than
something a site table can certify.
Output: two re-gated primitives, one new build guard armed in both builders, corrected numbers
and corrected prose in every place the false claim is asserted, and a reconciled threat record
across T-11-* and T-16-*.
</objective>

<scope_judgment>
## This gap is closed here, not deferred to Phase 16 — restated against the current record

**The original reasoning stands and is not repeated in full** (see `11-REVIEW.md` CR-01 and the
original 2026-08-17 draft of this plan for the complete four-point argument: the guard cannot be
armed with an exemption for the two live sites; deferring hands Phase 16 a dead probe and burns
the scarcest input the project has; the behaviour being made reachable is BD-02/BD-03's own
specified capture-and-restore loop, twice reaffirmed by user decision; and nothing here reaches
hardware sooner, while the recovery path — four `restore_managed_settings()` call sites, four
unenclosed Emergency Restore surfaces — is unchanged and structurally proven).

**What changed since that reasoning was written, and why it strengthens rather than weakens the
case for fixing this now.** Phase 16 already executed under the belief that this gate was fine.
It built `verify_capture_persistence()`, wrote `16-UAT.md` (12 tests, all blocked on DIST-03),
and shipped a MANIFEST claiming the capture-persistence fix makes `dimming()`/`silence()`
"load-bearing on a path with zero device evidence" — a claim that presupposes the path is
reachable at all. It is not, yet. Leaving the reachability defect in place any longer does not
merely delay a fix; it means `16-UAT.md`'s twelve tests, when someone eventually runs them on a
device, will observe nothing happening, EXACTLY the "dead probe" failure mode the original
scope judgment warned about — except now the probe has a phase number and a name attached to a
claim that it works. Closing the gap here, before the device session Phase 16 is still waiting
on, is what keeps that session from being wasted.

**What is deferred, explicitly, and unchanged from the original judgment.** The device proof of
the capture-and-restore loop — that `Get Device Details` returns a real correctly-typed value,
that the original is restored exactly on CLOSE, and that force-quit, restart, missed CLOSE,
overlapping sessions and lock-screen all restore or leave a safe value — remains **Phase 16**,
requirement **DIST-03**, `16-UAT.md`'s twelve tests. That deferral is recorded in
`docs/CAPABILITY-DECISIONS.md` by Task 4, not merely stated here.

**One human pause, unchanged from the original plan.** Task 2 is a blocking
`checkpoint:human-verify` sitting between the guard's proof and the gate fix. It does not reopen
whether Dim and Silence should work — that is settled and this plan does not re-litigate it. It
puts the measured before-and-after in front of a human at the one moment the environmental
writes stop being inert on a device that has never run them, and offers `defer` as a real
branch.
</scope_judgment>
