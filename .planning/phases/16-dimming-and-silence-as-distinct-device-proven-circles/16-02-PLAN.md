<objective>
Close, at rungs 1 and 2 and at zero device cost, the one genuinely open question about the
coercion shape this product's safety-critical writes depend on: is
`WFCoercionVariableAggrandizement` / `CoercionItemClass: WFNumberContentItem` correct at a
**direct Set-action float parameter**?

Research already narrowed this considerably. Donor 7.1 action 7 carries a coercion at a
non-conditional, direct action parameter (`getvariable.WFVariable`, `WFDateContentItem`), so the
mechanism is demonstrably not conditional-only, and the golden corpus shows eight named-variable
coerced instances across six parameter keys. The unwitnessed remainder is narrow and specific:
`WFNumberContentItem` at a float system-control parameter. Confidence is MEDIUM-HIGH, which does
**not** license skipping the check - operator/operand type validity is invisible in the plist and
only the UI reveals it. Gate B cannot help: `setbrightness` and `setvolume` are legacy identifiers
absent from the v78 first-party parameter catalog, so gate B applies no unknown-key check to them
at all and a clean gate B is not evidence about these sites.

Purpose: spend a free rung so the scarce device session is not spent on a question a simulator
could have settled.

Output: one archived spike with a signed, simulator-tested probe; a recorded verdict; corrected
rung-2 documentation; and a reasoned, evidence-backed disposition of the 11 uncoerced
`setvolume` sites.

**This plan touches no file under `tools/`, `src/` or `docs/*.py`.** It shares no file with plan
16-01 and runs in parallel with it.
</objective>
