<objective>
Implement locked decision **D-02**: remove `changed_at` and `changed_by_session_id` from
`settings_snapshot` entirely. Decided by the user on the standard rule that if the functionality
does not need it, it goes.

The trace behind the decision, so it is not re-litigated: there are **zero** consumers. No read of
state targets either field anywhere in either fork. The failure modes this phase exists to prove do
not need them either - overlapping sessions is already guarded by the has-any-value gate on the
whole snapshot dictionary, so a second session short-circuits and never overwrites a live original,
and every restore path gates on the original value being greater than zero. Neither guard consults
identity or time.

Removal is therefore a **three-site coordinated generator change**, not a delete of the writes
alone: the capture-arm writes, the bootstrap seed shape and its convergence recogniser, and the
seed-shape assertion in the phase5 checker. Done once at the generator level, both forks regenerate.

Removing a seeded leaf is safe **only because there is no reader** - this project's verified runtime
semantics make a dotted read of a missing segment a hard error. So the regression check that must
exist afterwards is a static assertion that no read targets a removed leaf. That assertion is the
real deliverable of this plan; the deletion is the easy half.

Purpose: retire dead state that plan 16-01 would otherwise have just made real for the first time.
Before the persistence fix these fields were written into a dictionary that was never saved, so they
did not survive the run that wrote them. Persisting the capture is precisely what would have given
them consequences - which is why removing them belongs in this phase and after 16-01.

Output: the leaves gone from writes, seed and assertion; a no-reader guard; the record corrected.

**Constraint D-MANIFEST:** `python3 docs/manifest_check.py` remains deliberately red until plan
16-05 re-signs and refreshes it. Do NOT edit MANIFEST rows.
</objective>

<reversibility rating="costly">
D-02 removes two seeded leaves from the shipped state shape. Re-adding them is a mechanical
generator revert with no migration needed - a device holding an older state file keeps the leaves
harmlessly, and a device holding a newer one simply lacks them, which is safe because nothing reads
them and the container and its groups are untouched. What makes it costly rather than free is that
the shipped state shape reaches devices, so a reversal means another rebuild, re-sign and re-import
cycle. It is **not** one-way, so no decision checkpoint is inserted; D-02 is in any case a LOCKED
user decision and a checkpoint here would re-litigate it.
</reversibility>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bootstrap seed shape → every later dotted read | A seed missing a segment turns every downstream dotted read into a hard runtime error with no try/catch to contain it. |
| `state.json` written by an older build → a newer build's run | A device may hold a state file whose shape predates this change. |
| generator (build time) → shipped state shape | The state shape is decided at build time and reaches devices; a wrong removal is discovered only at runtime, on a phone. |
