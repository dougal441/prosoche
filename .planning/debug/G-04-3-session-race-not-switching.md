## Symptoms

expected: Per canonical strategy §20 steps 2–6: open A, open B, close A, close B (scripted deliberately). If the active session ID changed (because B opened after A), the newer OPEN (B) owns state and the older CLOSE (for A) aborts without mutating state. Each new OPEN should correctly become the new active_session, and the corresponding CLOSE should correctly correlate with it.
actual: User reported (verbatim) - "doesnt look like the session id has changed once. i switched a to b to a close. open b to a to b. it kind of looks like it gets open, and gets close (because i get a menu popup) and then it's not doing next open? but, it's also hard to tell because we still have the test hardware pre-circles."
  In plain terms: the session ID in state.json does not seem to change across repeated open/close cycles, and it looks like only the FIRST open+close pair in the sequence registers - subsequent OPEN events after that first close do not appear to update active_session or produce a new session ID. Confidence is limited because the user also lacks a reliable indicator of whether OPEN/CLOSE actually fired at all (see related gap G-04-4b) - a confusing "Leaving / Continue" menu popup appears during this flow and its meaning is unclear.
errors: None reported explicitly, but a "Leaving / Continue" menu prompt appears mid-flow that the user could not interpret - note whether this menu is expected/intentional per the OPEN/CLOSE routing design or a bug.
reproduction: On device, rapidly - open tracked-app A, open tracked-app B, close A (switch back to A then close it), close B. Then repeat - open B, open A, open B. Inspect state.json's active_session / session id across the sequence.
started: Discovered during UAT of Phase 04 (close-pipeline-session-race), 2026-08-16. Related - the OPEN critical path (breadcrumbs A-J) was previously device-verified in isolation for a single OPEN reaching Circle 1 (build 2026-08-15o) - this is the first device test of the session-race / rapid-switching logic specifically.

## Resolution

root_cause: "close_pipeline()'s session-ownership check (tools/build_state_engine.py, lines 1160-1168, the conditional comparing 'Reloaded Session ID' to the entry-captured 'Captured Session ID') never wires WFConditionalActionString to the 'Captured Session ID' variable via token(). It is left holding the bare, unwired placeholder character alone (confirmed directly in the generated plist src/PROSOCHE-Dumb.xml, action 1251: WFConditionalActionString == '\\ufffc', a plain string, not the wired WFTextTokenString dict every analogous ownership check in the same file uses). Condition 4 ('string is') then compares the freshly-reloaded real session id against a literal one-character placeholder string, which can never match. Because CLOSE's sole owner-branch is the only place that appends to recent_sessions, sets last_close_at, clears active_session, restores settings, and saves state.json, this makes CLOSE a complete no-op on every invocation -- active_session is never cleared by CLOSE, so it only changes when a later genuine OPEN's unconditional overwrite replaces it. Secondary contributing factor (not required to explain the core symptom, but plausible during genuinely rapid app-to-app switching): open_pipeline()'s 2-second 'Genuine Open' debounce (lines 1019-1029) keys off a single global last_open_at rather than per-tracked-app state, so opening a DIFFERENT app within 2 seconds of the previous app's OPEN would also be treated as a non-genuine duplicate and skip session creation entirely."
fix: "Not applied (goal: find_root_cause_only). Suggested: in close_pipeline(), add owns_if['WFWorkflowActionParameters']['WFConditionalActionString'] = token('Captured Session ID') immediately after the existing '= \"\\ufffc\"' line (mirroring persist_contract() line 562, route_exit()'s create_owner line 843, and record_exit_and_route()'s owner line 872), then rebuild via tools/build_state_engine.py (subject to the project's git-merge-base build-provenance guard), re-sign, and re-verify on device per the CLOSE-pipeline UAT tests 3 and 6. Consider also adding WFConditionalActionString coverage to verify_conditional_inputs() (or a parallel check) so an unwired variable-vs-variable string comparison fails the build instead of shipping silently -- this is the recurrence guard this defect class is currently missing. Separately, consider whether the OPEN debounce should be keyed per-tracked-app rather than globally, given the canonical rapid-switch UAT scenario explicitly exercises two different apps within a short window."
verification: "Not run (diagnose-only). Direct evidence for the root cause itself: plistlib decode of src/PROSOCHE-Dumb.xml confirmed action 1251 ('Reloaded Session ID' conditional) holds an unwired WFConditionalActionString while all 14 other analogous ownership-check conditionals ('Contract Owner ID' x10, 'Exit Owner ID' x2, 'Create Owner ID' x2) hold the correctly wired token() structure."
